# 技术决策：多客户端 Monorepo

- 状态：已接受
- 日期：2026-09-11

## 背景

书法学习产品不等同于微信小程序。小程序只是一个 client；教师 Web、未来 iOS 等客户端也需要复用同一套用户与业务能力。

## 决策

仓库采用以下顶层边界：

```text
calligraphy/
├── apps/
│   ├── miniprogram/       # 目标：Taro + React + TypeScript
│   └── teacher-web/       # 目标：React + Vite + TypeScript
├── services/
│   └── api/               # 目标：NestJS + TypeScript
├── packages/
│   ├── contracts/
│   └── design-tokens/
└── docs/
    ├── product/
    ├── domain/
    ├── design/
    └── engineering/
```

本次只调整仓库结构。现有原生微信小程序代码原样迁入 `apps/miniprogram`；Taro、教师 Web 和 API 的实现及依赖安装留给后续独立任务。

微信登录由后端隔离：

```text
小程序 → wx.login() → temporary code → Backend → 微信服务器
                                      ↓
                              Identity → User
                                      ↓
                            产品 token/session
```

微信临时 code 不能作为用户标识。后端用 code 交换微信身份，再以 `provider + subject` 关联内部 User。未来新增 Apple 或手机号身份时，下游 Student、Pet、Assignment 不需要改变。

## 结果

- 每个客户端拥有独立的技术栈和发布生命周期。
- 后端成为业务能力与身份转换的边界。
- 公共 contracts 不携带平台 SDK 或微信敏感字段。
- 技术栈迁移与业务实现可以在后续任务中分别评审和验证。
